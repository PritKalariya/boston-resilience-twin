# ADR-024: DVC stages are generated from the DAG's step plan

- Status: proposed
- Date: 2026-10-27
- Owner: Kirtan10
- Phase: data

## Context

#18 asks for a `Data-Pipeline/dvc.yaml` that covers raw data, processed data and
labels, works as `dvc pull && dvc repro` on a clean clone, rebuilds every stage
from the public sources without remote access, and runs from `Data-Pipeline/`
with `.dvc/` at the repo root (ADR-017). It also asks that each step be defined
once: the stages and the #22 DAG tasks call the same script entry points.

The DAG already defines every real step in one place,
`pipeline_steps.step_plan`: the script, its arguments, the files it reads and
writes, the keys it needs and what to do when an input is missing.
`run_step` runs a plan: it checks the inputs, clears stale outputs, calls the
script's `main()` and logs rows in and out (#36). A hand-written `dvc.yaml`
would repeat every path and argument in that table, and the two would drift.

Until now nothing was tracked: `dvc.yaml` was an empty scaffold, and
`push_data` (#19) had nothing to push.

## Decision

- `Data-Pipeline/dvc.yaml` is generated by `Data-Pipeline/scripts/dvc_stages.py`
  from `step_plan` for the full build, and never edited by hand.
  `test_the_committed_dvc_yaml_is_what_step_plan_gives` fails when the
  committed file differs, so a change to `step_plan` regenerates it in the same
  PR (`python Data-Pipeline/scripts/dvc_stages.py`).
- Each stage runs `python scripts/pipeline_steps.py <step>`, which calls
  `run_step` for the full build, the same call the DAG task makes. So a stage
  gets the DAG's input checks (a missing file or key stops it, naming it), its
  output clearing and its log line.
- **deps:** the files `step_plan` reads (`data_in`, `config_in`) and the code
  that runs: `pipeline_steps.py`, the step's script and the pipeline scripts
  it imports at module level.
- **outs:** `data_out`, plus two new `StepPlan` fields: `keeps`, the folders a
  step adds to and keeps between runs (downloads, the statistics history), and
  `writes_too`, what else it writes (the static layer folder, manifests,
  change points, validation results). `keeps` and the 311 downloads
  (`keep_outputs`) are persist outs, so DVC keeps them when a stage runs again,
  as the DAG does.
- The legacy years are parsed in one stage per year, then `merge_legacy_311`,
  as in the DAG (#37). That gives 29 stages for 18 DAG steps.
- Left out, with the reason in `dvc_stages.LEFT_OUT`: `ingest_nws_forecasts`
  and `ingest_nws_alerts`. They save live snapshots that no public source can
  rebuild, and no stage reads them; the alert history comes from
  `ingest_alert_history` (ADR-014). The schedule state in
  `Data-Pipeline/data/state/` is not an out either: it records what one machine
  fetched and when, and is not data. The `bias_slicing` placeholder becomes a
  stage when #32 adds its script; the test then fails until #32 puts it in
  `STEPS`.
- Slices (`slices/<start>_<end>/`) are not stages; they are test runs of the DAG.
- `dvc repro` runs from `Data-Pipeline/`, where `dvc.yaml` and `dvc.lock`
  live; `.dvc/` stays at the repo root.
- `docker-compose.yaml` mounts `dvc.yaml` and `dvc.lock` read-only, so
  `push_data` pushes the outputs the committed lock names.

## Alternatives considered
| Option | Cost | Effort | Failure behavior |
|---|---|---|---|
| Generate `dvc.yaml` from `step_plan`, stages call `run_step` (chosen) | None | One generator script and a staleness test | A forgotten regeneration fails CI, not a run |
| Hand-written `dvc.yaml` calling each script with its arguments | None | Every path and argument written twice, 29 stages | The copies drift silently; a stage runs with arguments the DAG no longer uses |
| Hand-written `dvc.yaml` with `foreach` and `params.yaml` templates | None | Fewer lines, still a second definition | Same drift as above, and the DAG would have to read `params.yaml` too |
| The DAG runs `dvc repro` as its only task | None | Small | Loses per-task retries, failure alerts, rows-in-out logs and the parallel legacy years; Airflow is the decided orchestrator |

## Consequences

- A stage reruns when its inputs, its config or its code change. An edit to a
  shared script such as `pipeline_steps.py` reruns every stage on the next
  `dvc repro`.
- DVC orders stages by their files only. `validate_raw` reads the raw files, so
  `dvc repro` runs it, but the parse stages do not wait for it as the DAG
  tasks do. A failed check still fails `dvc repro`.
- `dvc repro` runs the stages one after the other: no parallel legacy years and
  no retries. It is for rebuilding and checking, not for the daily run.
- The ingest stages rerun only when their config or code changes or their
  outputs differ from `dvc.lock`; new days come from the DAG. Recording those
  as new data versions (`dvc commit` and a git commit of `dvc.lock`) is #40.
- Rebuilding from the public sources needs a free NOAA CDO token in
  `NOAA_CDO_TOKEN` (`docs/data-access.md`); without it `ingest_noaa_logan`
  stops and names the key.
- Pulled data comes without the schedule state, so the first DAG run on a new
  machine checks every source again.

## Revisit when

- #32 adds `bias_slicing`.
- #40 versions the DAG's runs, or the VM runs `dvc repro` itself.
- A step needs a slice of its own in DVC, or a stage becomes too slow to run
  in sequence.
